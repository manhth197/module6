## 4. Consent enforcement (M6-FAIL-002 / RULE-002) — fail-closed, with one binding gap

Both consent-gated growth paths reuse the hardened `ConsentGate.evaluate(snapshot, ConsentScope.CRM)` (the
M6.2B/M6.2D type-confusion fixes) and are **fail-closed** — absent/opt-out/expired/wrong-scope ⇒ excluded:

- **CRM repeat/reorder** ([crm.py:46](../impl/M6.2J/app/measurement/growth/crm.py)): CRM revenue counts a verified
  row only when the consumed CRM-eligibility flag **and** suppression flag are strictly `is True` **and** consent is
  VALID for the CRM scope. A `CRM_REORDER_SENT` / click / chat is never revenue; opt-out ⇒ 0 (SMK-008). No CRM send
  surface (`external_send=OFF`).
- **Dormant/reactivation** ([reactivation.py:44](../impl/M6.2J/app/measurement/growth/reactivation.py)): a member is
  eligible only with VALID CRM consent (fetched via the member's own `consent_snapshot_id`) **and** the consumed
  CRM-eligibility flag. Measure-only — rates/CPA floats; **`member_key` is never emitted** (aggregate counts only).

### F-SEC-2J-1 — borrowed consent: the CRM gate does not bind consent to the row's buyer *(primary; = boundary F-GROWTH-1; CODER)*

`CrmReorderMeasurement._crm_gate_passes(order_code)` evaluates the consent snapshot fetched by **`order_code`**
(`self._c.consent_by_order.get(order_code)`) but **never asserts `snapshot.subject_ref` equals the verified row's
buyer** (`customer_id`/`guest_id`). A VALID CRM consent belonging to a **different** subject, keyed to the order,
therefore authorizes the buyer's CRM revenue into the doc §9 CRM Revenue KPI — consent validated, but **not bound to
the data subject** it is meant to cover. This is a genuine consent-integrity gap in an in-scope FAIL-002 enforcement
point.

- **Why it is not a live FAIL-002 trip (fail_gate_tripped stays false):** `consent_by_order` is a **consumed** map
  owned by the Consent/CRM system — a channel attacker cannot inject or re-key it. The gap fires only if that trusted
  upstream map is **mis-keyed** (an upstream bug) or an in-process actor supplies an adversarial `CrmConsumed`; the
  shipped tests wire correctly-bound consent. So it is **armed-not-fired**, not a channel-reachable breach.
- **Why it still matters (net finding):** the codebase **already enforces this exact subject-bind elsewhere** — the
  M6.2E conversion seam requires `safe_subject_ref(snapshot) == customer_or_guest_key` (the F-D fix), and the Diamond
  path here already reads the row's `customer_id`/`guest_id`. The CRM growth gate simply **omits the bind** — a
  known-pattern-not-applied inconsistency at a consent checkpoint, not a theoretical one.
- **Fix (CODER):** in `_crm_gate_passes`, require `snapshot.subject_ref` to equal the verified row's
  `customer_id`/`guest_id` before counting, mirroring the M6.2E F-D discipline. Consider the same explicit bind on
  the reactivation path (it keys off the member's own `consent_snapshot_id`, a tighter binding, but still does not
  assert `subject_ref == member_key`).

## 5. PII handling — masking is correct on the report; one raw-attribute over-exposure

- **The shipped growth report carries no identity.** `GrowthReportBuilder.build()`
  ([growth.py](../impl/M6.2J/app/measurement/growth/growth.py)) emits only **aggregate KPIs** (rates, revenue sums,
  counts); `GrowthReport.to_public()` is `{"kpis": […]}`. No per-referral / per-member identity reaches the report or
  its export. The independent scan confirms 0 raw PII in every artifact.
- **Diamond buyer identity is masked on export.** `ReferralAttribution.to_public()`
  ([diamond.py:49](../impl/M6.2J/app/measurement/growth/diamond.py)) masks `buyer_ref` via the central `mask()` choke.

### F-SEC-2J-2 — raw `buyer_ref` on the public dataclass attribute *(= boundary N-1; CODER + owner, M6-OD-012)*

`ReferralAttribution.buyer_ref` holds the **raw `customer_id`/`guest_id`** (diamond.py:74:
`buyer = getattr(r, "customer_id", None) or getattr(r, "guest_id", None)`); masking is applied **only** in
`to_public()`, and the public `referral_attributions()` method returns the **raw-bearing objects**. A future consumer
that serializes a `ReferralAttribution` directly (evidence, log, a per-referral export) — instead of via
`to_public()` — leaks a raw first-party customer identifier. It is **not** exposed by the shipped aggregate report
(§5), so it is latent/armed-not-fired, but `buyer_ref` is a **direct customer/guest id** (higher sensitivity than a
platform psid), so opt-in masking is the weaker posture here. **Fix / decision:** make masking non-optional at the
identity boundary (store the masked form, or gate raw access), and ratify the export masking scope under M6-OD-012.
Same class as the M6.2I F-SEC-2I-2 trace-id finding; the boundary also routed the carried short-id / M6.2E
context-masking items here — all belong to the one M6-OD-012 masking-scope decision.

carried `handle_dashboard_request` does not itself authenticate (the HTTP/auth mapping is deferred to M6-OD-011), so
caller identity must be enforced at that seam, not trusted from the request body; and (b) apply the `buyer_ref`
masking discipline (§F-SEC-2J-2) at that export boundary. Mirrors the ACCESS-1 forward requirement raised at
M6.2G/H/I; stays a hard forward gate.

## 7. Untrusted-input handling — DATA, never instructions

The growth layer reads channel-derived `attribution_context` values (`entry_channel`, `referral_link_id`,
`diamond_id`) purely as data threaded into counts / attributions — never executed or interpreted. Event codes are
registry-validated upstream (RULE-001); `event_count` / `verified_rows` key off the row's own fields.
- *Cross-ref (CODER, not this reviewer's gate):* **F-GROWTH-5** — `GrowthReportBuilder.build()` duck-types every
  injected collaborator (`queue.all()`, `store.all()`, the mart reads) with no `isinstance`/Protocol guard, so a
  mis-wired **side-effecting** collaborator would run during `build()`. In-process only (the shipped `ReviewQueue` /
  `MeasurementEventStore` `.all()` are pure reads); fix with a Protocol/`isinstance` assertion so `build()` cannot be
  pointed at an action-bearing queue/store.
