**File**: `api/conversions.py:82-84,122-123` (pairs `customer_or_guest_key` + `consent_snapshot_id` straight from

non-consented subject's measurement authorised by someone else's consent) · **armed, not fired**.

The **audience** borrowed-consent was fixed (F-C: `subject_ref == member_key`); the **measurement** path has the
identical class and was **not** fixed — the CODER flagged it in IMPLEMENTATION_NOTES §4.3 as out-of-scope and
asked the boundary adversary to confirm. Executed (`MBC-endpoint`): a conversion with
`customer_or_guest_key = "victim_no_consent"` and `consent_snapshot_id = cs_valid` (a **different** subject's
VALID, in-scope consent) is CREATED, enqueued, and at dispatch `permits_send(cs_valid)` passes (that subject
consented) — so the victim's measurement reaches the transport and **2 PII-safe payloads + result-log records are
built** on borrowed consent.

**Why it is reported and why it is not a gate trip today.** It is **reachable from the untrusted conversions body**
(the endpoint accepts any `customer_or_guest_key` paired with any `consent_snapshot_id`) — a *more* reachable
surface than the audience F-C, which needed a mispointed CRM membership. But it is **armed-not-fired**: the
`StagedPlatformTransport` blocks every real send (external_send=OFF + no connector), so **no external measurement
actually occurs** — M6-FAIL-002 is not literally tripped. It becomes a live FAIL-002 the moment external_send
flips (M6.2E+).
**Fix (coder)**: bind `customer_or_guest_key` to `snap.subject_ref` (or a trusted mapping) in the measurement path
— at conversion creation and/or in the dispatcher's `_policy_block` — mirroring the F-C audience fix. The coder
committed to doing this fix-first at M6.2E (§4.3); this report **confirms the gap is open** and endorses that plan.

### 4.2 Observations (not defects — recorded so the owner decides knowingly)

- **O-1 — the identity hash is UNSALTED `sha256`** (`PII-unsalted-note`, hash_policy.py:22). A low-entropy
  identity (a phone / email) is brute-force-reversible from an unsalted hash — but (a) unsalted `sha256` is the
  platform (Meta CAPI) matching standard, and (b) the result log stores **no** `user_data`, so the hash lives only
  in the ephemeral payload. Privacy/legal review of the hash + a possible salt is **M6-OD-003 / M6-P1306** scope.
- **O-2 — `platform_event_id` excludes `customer_or_guest_key`** (`DD-source-collision`, payload.py:21). Two
  *distinct* conversions that share `(source_event_id, event_code)` but differ in customer collide onto one
  `event_id`, so the platform would **under-count** them. This is the fail-closed direction (under- not
  over-count, so not FAIL-001) and needs a **reused `source_event_id`** (a data-integrity fault upstream). A
  data-quality note for M6-P1306 / the DQ checker (M6.2F).
- **O-3 — forcing `config.EXTERNAL_SEND="ON"` marks the item `WOULD_SEND` but transmits nothing** (`OVR-force-on`,
  platform_transport.py:44-56). With the flag flipped, the transport records `WOULD_SEND` and returns without
  raising — but there is **no connector / network code** (line 56 is a comment), and the tokenizer sweep finds
  **0** network/db primitives across the M6.2D tree (`OVR-sweep-net`). The real hard lock on a real send is the
  **connector absence (M6-OD-004)**, not the flag alone.
- **O-4 — a staged held item re-drains and appends a new `BLOCKED` result-log record every `run_once`**
  (`W-heldlog-growth`, records 2→4 over two drains). While `external_send=OFF`, an `ExternalSendBlocked` item stays
  QUEUED and is re-processed each drain, re-building the PII-safe payload and appending another BLOCKED record →
  unbounded `BLOCKED` records. Staged-only (an `ON` item would SEND, not hold) and PII-safe, so not a gate trip — a
  result-log / DQ hygiene note for M6.2F / the owner.
