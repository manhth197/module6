## 3. Verdict per in-scope fail gate

### M6-FAIL-001 — Revenue misuse (verified-only revenue, RULE-003) — **NOT TRIPPED**

- **Verified-only choke holds through the real path.** A `QUOTE_SENT` (+ mapped spend), an `ORDER_CREATED` draft,
  and the full fail-gate taxonomy (`quote / cart / order-draft / payment-waiting / COD-waiting`) all produce
  `revenue_verified = 0.0`; ROAS is `0.0` (0 verified revenue / real spend — the correct, non-inflating value the
  tester's SMK-004 asserts) or `None` (no spend), never a positive fabricated number. Quotes still count in the
  **funnel** (measured), never in revenue (A1–A3).
- **The materializer refuses revenue on a non-ORDER_VERIFIED conversion** — a `QUOTE_SENT` conversion carrying
  `revenue_value=999999` books nothing (`row.revenue_value=None`, mart total `0.0`) (A4).
- **The store is the single revenue writer:** `insert()` rejects a revenue-bearing Zone-A row; `materialize()`
  writes revenue only with `verified=True` **and** an `order_code`, then **set-once** (a different revenue raises
  `MeasurementStoreViolation`); the row is **frozen** so a dashboard consumer cannot re-staple revenue (A7).
- **Defence-in-depth:** the DQ **Verified-Revenue** item independently FAILs any revenue on a non-`ORDER_VERIFIED`
  event, or an `ORDER_VERIFIED` without `order_code` → overall **FAIL** (A8, SMK-015/004/005).
- **CRM / Diamond revenue are verified-only subsets**, never summed into Revenue Verified (no double count) (A11).

The residual event-code / aggregation gaps (F-DASH-1, F-DASH-3) are **armed-not-fired**: the materializer is
constructed **only in tests** and is the sole `store.materialize` caller — **no channel path books mispaired
revenue in the staged app** (§4). They do not trip FAIL-001 today.

## 4. The primary residual — F-DASH-1 (armed-not-fired; the sharpest finding)

**What:** `AttributionMaterializer.materialize(event, conversion)` books revenue onto `event.event_id` while
deriving `verified` **from `conversion.event_code`** — it **never asserts the measurement event's own
`event_code == ORDER_VERIFIED`** (nor `event.event_code == conversion.event_code`). Executed: pairing an
`ORDER_VERIFIED` conversion with an `ORDER_CREATED` / `PAYMENT_WAITING` / `COD_WAITING` measurement event books
`500000` onto the pre-verified row (W1). The store shares the gap — `materialize` trusts the caller `verified`
bool and never re-reads the row's `event_code` (A6). This generalises A5 (widened `verified_event_codes`) and the
carried **M6.2E O-4**.

**Amplifier (also executed):** the dashboard's `_dashboard_data_quality` validates only that each displayed metric
carries a trace + sample evidence — it does **not** run the 8-item per-row DQ gate. So a mispaired revenue row would
display as **Revenue Verified with overall `PASS`**, while the DQ **Verified-Revenue = FAIL** is a *separate*
artifact the endpoint never consults. The DQ gate is therefore **not a backstop for the dashboard revenue path**.

**Why it is NOT a live FAIL-001 breach (reachability, verified on the real wiring):**
`grep` over `app/` proves `store.materialize(` has exactly **one** caller — `materializer.py:69` — and
`AttributionMaterializer(` is constructed **only** in `tests/conftest.py`. **No endpoint or orchestrator in the
staged app wires the materializer**; the conversions endpoint only creates conversion rows and enqueues to the
outbox. Hence, in the running staged slice, **no request can cause a non-`ORDER_VERIFIED` row to acquire
`revenue_value`**, and no such row exists for the dashboard to sum. The gap is a **latent contract-hardening**
issue for the future owner-integration assembler.

**Fix (CODER):** in `materialize`, assert `getattr(event, "event_code", None) == _ORDER_VERIFIED` (or
`== conversion.event_code`) before booking revenue; optionally have the store re-derive `verified` from the row's
own `event_code`; and consider surfacing the per-row DQ Verified-Revenue verdict into the dashboard `overall`.

## 6. Residuals & notes (none trips an in-scope gate)

**OPEN residuals — armed-not-fired (routed):**
- **F-DASH-1** *(primary, CODER + M6-P1506/M6.2G)* — materializer/store book revenue without asserting the
  measurement event's `event_code==ORDER_VERIFIED`; the dashboard `overall` never runs the per-row DQ gate. See §4.
- **F-DASH-2** *(CODER + M6-P1506)* — `attribution_context` is a plain mutable dict inside a frozen row; in-place
  mutation defeats the "set-once immutable snapshot" claim (upgrades DQ Attribution, re-routes CRM/Diamond
  breakdown). Fix: store as `MappingProxyType` / copy-on-read.
- **F-DASH-3** *(CODER / DQ)* — `revenue_verified()` sums per-row while `verified_order_count()` dedups by
  `order_code`; two verified rows sharing an order double-count Revenue Verified + AOV. Fix: dedup revenue by
  `order_code`, or guarantee one verified-revenue row per order upstream (the DQ Dedup item is the per-row backstop).
- **F-DASH-4** *(M6.2G / M6-P1600 + CODER)* — `is_scale_evidence_eligible` consults only attribution confidence,
  not the 8-item DQ overall; a consent-missing / suppression-unreflected row is still "scale eligible". Not
  consumed in-slice and AND-gated by `SCALE_MODEL_RATIFIED=False`; the **mandatory M6.2G scale re-gate** must close
  it before any real scale.

**Notes:**
- **N-1** NaN/Inf revenue poisons the total + breaks idempotent replay (carried **M6.2E O-5**) → DQ robustness, M6-P1506.
- **N-2** negative revenue accepted (understates, never inflates); no `≥0` check in store/DQ → M6-P1506.
- **N-3** `object.__setattr__` / bare `config.SCALE_MODEL_RATIFIED` are in-process mutable — `frozen`/`Final` are
  defence-in-depth, not hard barriers; both require arbitrary in-process code execution (out of the channel model).
- **N-4** `mask` reveals first-3 + last-2, i.e. 5/6 chars of a 6-char id → PII hardening, M6-P1506.
- **N-5** an empty-store dashboard reports overall **FAIL** (an evidence-less `0` is not silently PASS) — fail-closed,
