## 3. Verdict per in-scope fail gate

### M6-FAIL-002 — Consent violation (RULE-002 fail-closed) — **NOT TRIPPED**

- **CRM revenue is consent + eligibility + suppression gated.** An OPT_OUT / EXPIRED / MISSING / absent consent
  snapshot → `crm_revenue() == 0.0`; a VALID consent granting only `audience_sync` (not the CRM scope) → excluded;
  a missing/False CRM-eligibility flag → excluded; a missing/False suppression flag → excluded; a truthy-but-not-True
  flag (`1` / `'yes'`) → excluded (strict `is True`); only all-pass counts (A1–A9, SMK-008). The CRM layer exposes
  **no** send/sync/dispatch/crm_send surface.
- **Reactivation is consent + CRM-eligibility gated** — only a member with VALID CRM consent **and** the consumed
  CRM-eligibility flag is eligible; opt-out / not-eligible excluded; measure-only (rate/CPA floats; member_key never
  emitted) (D1–D2).
- The consent gate itself is hardened against the str/subclass/`__contains__` type-confusion class (the M6.2B/D F2/F-B
  fixes) — verified indirectly through the CRM path.

The residual **F-GROWTH-1** (borrowed consent, §4) does not trip the gate: it needs a mis-keyed/adversarial consumed
consent map (a trusted upstream input), not a channel.

### M6-FAIL-004 — Core override / commission (RULE-019) — **NOT TRIPPED**

- **No commission is computed.** The Diamond layer exposes **no** commission amount/rate/payout method (B1); a token
  sweep of the growth package finds **0** commission/pricing/order-state/member-right override defs (B4, E1).
- **`commission-ready revenue` is a REVENUE figure, not a commission** — the subset of verified referral revenue
  whose consumed commission-eligible flag is True (`commission_ready_revenue ≤ diamond_revenue`); fail-closed to 0
  without the consumed flag (B2–B3, SMK-014). Commission eligibility is a **consumed** Finance-owned flag M6 reads,
  never decides (B6).
- Buyer identity is masked on the referral export (B5); the growth report carries no override field.

### M6-FAIL-005 — Data Mart abuse (RULE-012 support view only) — **NOT TRIPPED**

- The `DataMart` and the `GrowthReportBuilder` expose **no** trigger/send/sync/scale/publish/order-state/write verb

## 4. The primary residual — F-GROWTH-1 (armed-not-fired; the sharpest finding)

**What:** `CrmReorderMeasurement._crm_gate_passes` calls `ConsentGate.evaluate(snapshot, ConsentScope.CRM)` but
**never binds `snapshot.subject_ref` to the verified row's buyer** (`customer_id`/`guest_id`). Executed: a consent
snapshot belonging to a **different** subject (`person_B`), VALID + CRM, keyed to the order, authorizes the buyer
(`person_A`)'s CRM revenue straight into the exported doc §9 CRM Revenue KPI — `crm_revenue() == 650000` (W1).

**Why it is NOT a live FAIL-002 breach (reachability):** `consent_by_order` is a **consumed** map owned by the
Consent/CRM system; M6 records it. A channel attacker cannot inject it. The gap fires only if that upstream map is
**mis-keyed** (an upstream bug) or an in-process actor hands the growth layer an adversarial `CrmConsumed`. The
shipped tests wire correctly-bound consent. So it is armed-not-fired.

**Why it still matters:** the M6.2E **conversion seam already enforces this exact subject-bind** (the F-D fix:
`safe_subject_ref(snap) == customer_or_guest_key`), and the Diamond path already reads the row's
`customer_id`/`guest_id` — but the CRM growth path **omits the bind**. It is the report-surface realization of a
borrowed-consent gap. **Fix (CODER):** in `_crm_gate_passes`, require `snapshot.subject_ref` to equal the verified
row's `customer_id`/`guest_id` before counting, mirroring the M6.2E F-D discipline.

## 6. Residuals & notes (none trips an in-scope gate; all armed-not-fired)

**F-GROWTH-1** *(CODER, primary — W1).* Borrowed consent: bind `snapshot.subject_ref` to the verified row's buyer
in `_crm_gate_passes`, mirroring the M6.2E F-D fix. See §4.

**F-GROWTH-2** *(CODER + M6-P1906 — W2).* Two `crm_revenue` methods exist — the gated growth one (used by the §9 KPI,
correct) and the consent-blind `DataMart.crm_revenue` (a carried M6.2F channel-breakdown aggregate) reachable via
`builder._mart`. The shipped report is correct; the risk is a future consumer labeling the ungated number "CRM
Revenue". **Fix:** rename/mark the ungated aggregate (e.g. `crm_channel_revenue`) or gate it.

**F-GROWTH-3** *(CODER — W3, extends D3).* `reads.verified_rows` keys off `revenue_value is not None` (the M6.2F-style
choke), **not** `event_code == 'ORDER_VERIFIED'` (the M6.2I self-enforcing choke). Combined with the materializer
deriving `verified` from `conversion.event_code`, a mispaired (ORDER_VERIFIED conversion, QUOTE_SENT event) call
stamps revenue onto a quote-content row, which the growth layer then counts as CRM/Diamond/commission-ready revenue.
Not channel-reachable (the materializer is constructed only in tests) and FAIL-001 is out-of-scope for this slice —
but it reaches a **Finance-facing commission-ready figure** and is a **RULE-003 cross-slice consistency regression**
vs M6.2I. **Fix:** `verified_rows` should AND `event_code == 'ORDER_VERIFIED'` with revenue presence (adopt the
M6.2I lesson).

**F-GROWTH-4** *(CODER + M6-P1906 — W4).* The Learning-Engine "Candidate approval rate" KPI reads
`review_state.value == 'APPROVED'` only, never `is_publish_authorized` or the audited `OwnerReviewDecision`, so a
candidate marked APPROVED at construction (no decision, safe-range UNKNOWN) inflates the rate. A measurement-integrity
gap only — it publishes nothing (the M6.2H `is_publish_authorized` still gates the real publish). **Fix:** count only
candidates with a bound audited decision (and/or `is_publish_authorized`).

**F-GROWTH-5** *(CODER — W5).* `GrowthReportBuilder.build()` duck-types every injected collaborator
(`queue.all()`, `store.all()`, the mart's reads) with no `isinstance`/Protocol guard, so a mis-wired side-effecting
collaborator would run during `build()`. Needs control of the composition root (the shipped `ReviewQueue` /
`MeasurementEventStore` `.all()` are pure reads). **Fix:** an `isinstance`/Protocol assertion so `build()` cannot be
pointed at an action-bearing queue/store.

**Note — N-1** *(M6-P1906 — W6).* `ReferralAttribution.buyer_ref` holds raw PII on the public dataclass attribute;
`mask()` is applied only in `to_public()`. A caller reading `.buyer_ref` directly gets the raw customer/guest id.
The carried masking findings (short-id over-disclosure; the M6.2E context masks only `psid`) also route to M6-P1906.
