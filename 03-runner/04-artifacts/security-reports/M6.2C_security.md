## 3. Pillar 1 — Raw PII scan (RULE-014 / H02) — **CLEAN (O-2: outbox rows verified)**

The core M6.2C PII question (boundary O-2): **does raw PII land in a durable outbox row / key / audit?** Verified:

- **Measurement outbox row (`MeasurementOutboxItem`) — PII-clean.** `payload_ref = "conversion:{conversion_id}"` (a
  reference, not a payload); `dedup_key` is a **sha256** (`enqueue._hash_key`); `source_event_id`/`idempotency_key`/
  `consent_snapshot_id` are opaque refs. The identity component (`customer_or_guest_key`) is **only hashed into** the
  dedup key, **never stored** on the row.
- **Audience outbox row (`AudienceOutboxItem`) — one raw identity ref by design.** `member_key` is stored raw
  (`enqueue.py:134`), because it is the audience-match identity the hashed payload is built from **at dispatch in
  M6.2D**; `dedup_key` hashes it (segment_id+member_key+platform+operation → sha256); `payload_ref="segment:{id}"`.
- **`conversion_events` — one raw identity ref by design.** `customer_or_guest_key` (PII, masked on export) — a
  dedup-key component, hashed into `measurement_dedup_key` and the conversion replay key.
- **Masked on every export.** All identity refs reach the audit sink only through `audit.record(subject=…)` (masked)
  and `_corr(correlation_id)` (masked); outbox/dispatcher audit `detail` carries only `outbox_id`/`segment_id`/
  `op`/enum reasons. The §2 sink sweep confirms **nothing serializes/logs/exports** these rows.

**Conclusion:** no raw PII lands in a durable-exported row/key/audit in this slice. The two raw identity refs sit only
in **in-memory** (staged; `live_migrations=false`) operational rows, masked on export, hashed in keys — the same O1 /
M6-OD-012 design as M6.2A/B, now extended to the outbox/conversion layer. Recorded as **O-2** (§7): a forward
requirement (OD-012 masking + OD-003 hashing govern the M6-OD-011 durable binding and the M6.2D send), not a leak.

### F-B — a lying `set`-subclass `consent_scope` defeats the F2 guard (consent fail-OPEN, armed-not-fired) — concur → CODER
**File**: `consent/gate.py:56-68`. **Rule/gate**: RULE-002 / M6-FAIL-002 · **Direction: fails OPEN**.
Consent enforcement is in my scope, so I concur with boundary F-B: the F2 guard checks the scope container's **type**
and **element types**, but `scope not in snapshot.consent_scope` dispatches to `__contains__`; a `set` subclass with a
lying `__contains__` and an **empty backing** (so the element check is vacuously true) passes F2 and grants a scope it
never held → `permits_send` True → SENT (with an injected transport). **Ceiling:** armed-not-fired — the staged
transport blocks, and a real `ConsentSnapshot` coerces its scope to a plain `frozenset` in `__post_init__`, so only a
**compromised consent adapter** can produce this; it becomes live only at M6.2D against a hostile consent
system-of-record. **M6-FAIL-002 not tripped today.** **Fix (CODER):** `scope in frozenset(snapshot.consent_scope)` —
materialize before the membership test (the gate-level completion of F2).

### F-C — the audience path never binds `member_key` to the consent subject (borrowed consent, fail-OPEN, armed-not-fired) — concur → CODER
**Files**: `outbox/enqueue.py:122-129`, `outbox/audience_dispatcher.py:75`. **Rule/gate**: RULE-002 / M6-FAIL-002 ·
**Direction: fails OPEN**. `enqueue_audience_sync` fetches the snapshot by `member.consent_snapshot_id` and evaluates
it, and the dispatcher's `permits_send` checks `current_state(snap.subject_ref)` — **the snapshot's** subject, never
asserted to be **the member**. A segment-membership row that (mis)points a member at another subject's VALID consent →
that member is ADDed on **borrowed consent**. The measurement path binds consent to the event's subject (M6.2A
MAJOR-2); the audience path never received that fix. **Ceiling:** armed-not-fired — staged transport blocks; needs a
**mispointed CONSUMED membership** (`customer_segment_members`, RULE-018, M6 only reads it). **M6-FAIL-002 not tripped
today.** **Fix (CODER):** bind `member.member_key` to `snap.subject_ref` (or a trusted mapping) before treating a
member as ADD-eligible, mirroring the ingest seam's `_subject_bound`.
