## 4. The mapper — fail-closed, PII-safe, no-HTTP, no-secret (verified on the code)

`recall_risk_mapper.py` is a security-positive read layer:
- **Reads presence booleans only.** `map_risk_flags` reads `recall_hold`/`sale_lock`/`quality_hold`/`recall_case_open`;
  `decision`/`block_reasons`/`sku_ref` are RECORDED for provenance and **never read** (M6 does not own the recall
  decision — RULE-018, no fabricated lock). A `decision=SELLABLE` cannot clear a present `recall_hold`; a scary decision
  string cannot fabricate a lock.
- **Strict-bool choke.** `_as_bool` returns the value only if `isinstance(value, bool)` — `0`/`1`/int/`"false"`/`None`
  all → None → INCOMPLETE (never `bool()`-coerced to a clear or a lock). Centralized in `map_risk_flags`, so both the
  value-object and the dict paths flow through it.
- **Fail-closed on pull outcome.** `map_pull_outcome` models the S1b seam's TIMEOUT/HTTP_429/CONNECTION_ERROR/absent/
  malformed/unrecognized → INCOMPLETE (empty), with **no HTTP** — never a False false-clear, never a fabricated True.
- **Fail-closed by construction.** `recall_risk_contribution` returns the map only when an active lock is present (FAIL
  direction) or the full 6-lock picture is clean (`risk_picture_complete`); an incomplete/bare-clean read collapses to
  `{}` (Scale-Gate HOLD, never a false PASS). This was the red-team MAJOR fix — the mapper's clean output is
  structurally never a standalone clearing map.
- **No transport, no secret.** The module imports only `conditions.RISK_LOCKS` (with an import-time drift guard) — no
  HTTP/queue/transport import; the S1b live client to ops-core is not built. No credential literal (scan §3).

**FAIL-006 relationship:** the mapper cannot enable an auto-scale — a present lock → gate FAIL (RULE-017 veto), an
incomplete read → gate HOLD; it holds no executor/budget/campaign handle.

## 6. F-SEC-2R-1 (primary, = boundary N5) — the carried scale-decision export is unmasked

**`evidence_ref`** **verbatim**. The `reason`/`audit_ref` flow from the **untrusted admin body** — `handle_scale_decision`
copies the request fields into `OwnerDecision` — so a PII-shaped reason typed into the admin body would export unmasked
on the durable/export surface.

- **This is not new to M6.2R.** `OwnerDecision` is the carried scale-gate decision (M6.2G, byte-identical this slice);
  the boundary re-surfaced it because the recall-risk work feeds the same Scale Gate. It is the **exact same
  durable-export masking-scope family** as my **M6.2Q MC-09** (`AdsSpendImportDecision.to_public()` — reason/audit_ref
  raw), and as F-SEC-2K-1 (`status`) / F-SEC-2M-1 (`smoke_id`) / the trace-id family — all → **M6-OD-012**. The
  decision-object export gap is now a **two-instance pattern** (scale `OwnerDecision` + spend `AdsSpendImportDecision`).
- **The fix is already known.** The **audit sink already drops** `reason`/`audit_ref` (machine-safe — the scale-gate
  and spend-gate audit hardening); `to_public()` should mirror it (mask/drop, or route the free-text through the
  raw-PII tripwire at intake). *Reachability:* channel-reachable at the data-flow level (untrusted admin body →
