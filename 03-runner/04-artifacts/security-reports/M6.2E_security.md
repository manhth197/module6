## 7. Findings (detailed)

### O-2 — durable Zone-B `attribution_context` keeps raw `psid` (Observation → M6-OD-012 / forward, my scope)
See §3. **Not a leak today** (in-memory staged store; masked on every export via `to_public()`; the attribution layer
has no sink). **Forward (CODER / owner):** enforce M6-OD-012 masking on any export/serialization of an
attribution snapshot before the M6-OD-011 durable binding; keep the `as_stored()`/`to_public()` split (durable raw for
trace joins, masked on export).

### O-2b — export masks only `psid`, not `messenger_thread_id` / `comment_id` / `live_session_id` (my add → M6-OD-012)
`to_public()` masks `psid` but exports the other channel refs raw. They are channel **object** ids (not user ids), so
this is a defensible line — but a `messenger_thread_id` (and, if ever captured, a comment author) can resolve to a
person. **Recommendation:** make the M6-OD-012 masking policy state explicitly whether conversation/thread identifiers
are in scope for masking, and align `to_public()` to it. Not a present leak (in-memory; object refs).

### O-1 — `AdjustmentRecord.proposed` has no field allow-list (Observation → CODER hardening, my scope)
A caller may place an arbitrary key (e.g. `commission_value`) in `proposed`; it is **stored but never computed or
applied** to any row, so RULE-019 (no commission *math*) holds — the module records a caller *assertion*. **Fix:**
constrain `proposed` to the attribution/revenue field set (and mask/annotate it as non-PII), so a stray PII or a
commission value cannot be parked in an audit record.

### F-G — adjustment path under-validated (MINOR, accountability/immutability-completeness) — cross-ref → CODER
`materializer.request_adjustment` / `adjustment.py` accept **empty** required fields (actor/reason/audit_ref/
evidence_ref=""), do **not** check the target row **exists or is verified**, and store `proposed` as a **post-hoc-
mutable** `dict`. **Never mutates the verified row** → **not FAIL-004** (accountability/completeness only). **Fix
(CODER):** reject empty/whitespace required fields; assert the target exists+verified before recording; store
`proposed` immutably (`MappingProxyType`/copy). Ties to O-1.

### O-5 — non-finite `revenue_value` breaks set-once replay (Observation → M6.2F / CODER)
`NaN != NaN`, so an honest replay of a NaN-revenue verified row is seen as a *different* value and raises. Root cause
is non-finite revenue (the M6.2D O-4 DQ gap). **Fix:** reject a non-finite `revenue_value` (`math.isfinite`) at the
conversions endpoint / DQ checker. Not a FAIL-001 over-count.

### O-3 — carried ingest raw-subject compare (FAIL-002-adjacent) — cross-ref → CODER
`ingest.py`/`identity/resolver.py` compare `snapshot.subject_ref == guest_id` on the **raw** value (not via
`safe_subject_ref`); a hostile `ConsentSnapshot` subclass with a raising `subject_ref` property could raise there.
Out of this prompt's FAIL-001/004 scope, armed-not-fired (external_send=OFF), coder-flagged for later hardening —
recorded so it is not lost.

### Revenue / immutability / commission — corroboration (the in-scope pillars)
FAIL-001 and FAIL-004 are held (executed by M6-P1405, concurred from code): revenue only from `ORDER_VERIFIED`,
set-once; LOW/conflict never scale evidence (doubly fail-closed); adjustments are append-only overlays that never
mutate the verified row; no commission computed / no Core write. `verified_event_codes` is a constructor default
(`ORDER_VERIFIED`), not channel input — a mis-wire would be a wiring fault (**O-4**, CODER/integration), not a
channel-reachable FAIL-001.
