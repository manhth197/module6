M6.2G adds the §19 admin endpoint **`POST /api/admin/ads/scale-requests`** (M6-CTR-019, "Tạo đề nghị scale | Owner
approval required") with two handlers: **create** (compute conditions + propose an inert request) and **decision**
(record an explicit owner APPROVE/REJECT). Both are **framework-neutral / inert**:

- **No executable path (RULE-010 / FAIL-006):** `ScaleRequestDeps` holds only the `ScaleGate` (over the inert store) +
  the server-assembled `ScaleContext` + audit — **no** Transport / budget / campaign / audience handle.
- **Conditions are server-side (RULE-H03):** they come from `deps.context`, **not** the untrusted admin body — a
  request body can never fake a condition PASS (boundary D1).
- **Owner discipline:** the decision handler requires **all** of `actor`/`reason`/`audit_ref`/`evidence_ref`, rejects
  a bad decision kind, and surfaces a Risk-veto refusal as `APPROVAL_REFUSED` (never a silent pass). The system never
  synthesizes an approval (RULE-015).

**ACCESS-1 (the load-bearing forward requirement, my emphasis).** The decision handler takes **`actor` from the request
body** as the deciding owner's identity; there is no authentication that the caller **is** that owner. Inert today (an

binding this becomes the **most important authz control in the slice**: the endpoint MUST authenticate the caller and
authorize **APPROVE to the owner role only**, and bind the recorded `actor` to the authenticated identity — because an
APPROVE is the owner's authorization for a scale performed **outside** Module 6. A weak binding would let a non-owner
record an owner APPROVE. Named as a required deferral, alongside the F-SCALE-2 re-evaluate-on-load requirement.

## 7. Findings (detailed)

### ACCESS-1 — owner-decision endpoint must authenticate the owner at the M6-OD-011 binding (forward requirement, my emphasis)
See §6. Not a present exposure (staged; inert; no executor). **Requirement (owner / M6-OD-011):** authenticate the
caller on `POST /api/admin/ads/scale-requests` (decision path), authorize APPROVE to the owner role, and set the
recorded `OwnerDecision.actor` from the authenticated identity — never trust a body-supplied `actor`.

### F-SCALE-PII-1 — owner free-text (`reason`/`audit_ref`/`evidence_ref`) echoed unmasked on export (Observation → CODER + M6-OD-012, my finding)
**Files**: `scale/models.py` (`OwnerDecision.to_public`), `migrations/0010_create_ads_scale_approval.sql`. Owner
annotations, contract-non-PII, and excluded from the audit (D5) — **no leak today**. **Fix (CODER):** document the
field contract ("owner annotation, non-PII") and/or bound + mask `reason`/`audit_ref`/`evidence_ref` on the export
surface, consistent with the M6.2A SEC-PII-02 treatment of a free-text field and M6-OD-012.

### F-SCALE-3 / F-SCALE-4 — unvalidated `budget_cap` / presence-only `rollback_condition` (MINOR, armed-not-fired) → CODER
Untrusted-input gaps at the create handler (RULE-H03): `budget_cap` accepts `-1/0/+inf/NaN`; `rollback_condition`
accepts whitespace. Both are **inert today** (no executor consumes them; `is_scale_authorized` is always False), but
they weaken the RULE-010 budget-cap + rollback safety pairing that the owner relies on at integration. **Fix (CODER):**
`math.isfinite(budget_cap) and budget_cap > 0`; content-validate `rollback_condition`.

### F-SCALE-1 — risk fresh-read completeness (MINOR, armed-not-fired) → CODER
`_assert_risk_clear_at_approval` refuses on an active fresh lock and clears only on a **complete** fresh read, but an
**empty/partial** fresh read falls back to the *proposal's* Risk condition (stale). No scale is authorized regardless
(overall HOLD). **Fix (CODER):** require a complete fresh risk read to approve (refuse on empty/partial) rather than
falling back to the proposal — closing the RULE-017 re-check completeness.

### Cross-reference (concurred; in-process only)
**F-SCALE-2** — `ScaleRequestStore.update_state` doesn't pin `target/cap/condition_results` on a transition, so an
in-process `replace()`+`update_state` can bait-and-switch an APPROVE onto a larger target/cap. **Not wire-exposed**
(the gate's own path changes only approval_state/decision/decided_at) and **inert** (no executor). The closest shape
to a real FAIL-006 **if an executor is ever wired**. **Fix (CODER + M6-OD-011):** reject transitions that mutate
target/cap/condition_results; the persistence binding should **re-run `evaluate_conditions`** on load, never trust a
stored `overall_status`.

### FAIL-006 / F-DASH-4 — corroboration (the in-scope pillar + the M6.2F carry-forward)
FAIL-006 is held (boundary executed 5 independent reasons; concurred from code — no executable path, `is_scale_authorized`
structurally unreachable, no consumer, nothing wire-forgeable). **My M6.2F finding F-DASH-4 is closed**: the scale
gate's Quality condition requires `dq_overall == PASS`, so a DQ HOLD/FAIL row can never reach a scale-ready PASS — the
scale gate is the mandatory re-gate that incorporates the DQ overall the attribution-level `is_scale_evidence_eligible`
ignored.

### Untrusted-input handling
The create handler validates the body server-side (scale_target required; budget_cap number-not-bool) and computes
conditions from server state, not the body. The residual validation gaps are F-SCALE-3/4 (routed). No untrusted value
reaches a sink or authorizes anything.
