## 6. Findings (none trips an in-scope fail gate; all armed-not-fired)

### F-SEC-2I-1 — cross-person trace stitch *(primary; = boundary F-FUNNEL-4; CODER + owner)*

`GoldenHourFunnel._trace` ([funnel.py:168](../impl/M6.2I/app/measurement/funnel/funnel.py)) folds each identifier
**independently** across **all** events grouped under one `live_session_id`:

```python
comment_id = comment_id or ctx.get("comment_id")
messenger_thread_id = messenger_thread_id or ctx.get("messenger_thread_id")
psid = psid or ctx.get("psid")
```

`live_session_id` is a **session-level shared key** (one live broadcast has many viewers/commenters), and the fold
has **no subject binding** (no `customer_or_guest_key`). So when a session carries events from more than one
person — the normal case for a live broadcast — the exported `FunnelTrace` stitches **person A's `comment_id`**
next to **person B's `messenger_thread_id`** (and person C's psid) into a single record, **asserting a false
association between distinct identifiable people**. Masking psid does **not** cure this: the harm is the fabricated
linkage itself (attribution-integrity + PII-association), and `comment_id` / `messenger_thread_id` are exported raw
(§F-SEC-2I-2). It is armed-not-fired for a **hard** breach only because the canonical tests use one-subject
sessions; it becomes real the moment a shared session key spans >1 subject.
**Fix (CODER):** bind the trace to a single subject (the conversion's `customer_or_guest_key`), or record
per-subject traces. Does **not** trip FAIL-001/010 (revenue and phase-order are keyed off each row's own fields).

### F-SEC-2I-2 — raw trace-id export / masking-scope inconsistency *(CODER + owner, M6-OD-012)*

`FunnelTrace.to_public` ([models.py:38](../impl/M6.2I/app/measurement/funnel/models.py)) masks **only** `psid`;
`comment_id`, `messenger_thread_id`, `live_session_id` are exported **raw**. `messenger_thread_id` is a **per-person
Messenger conversation handle** — the same identity-boundary family as `psid` (it resolves 1:1 to one person's DM
thread). Masking `psid` as PII while exporting `messenger_thread_id` raw is an **inconsistency**: if one is PII the
other deserves at least parity. `comment_id` / `live_session_id` are more plausibly opaque platform/session ids
(lower sensitivity), but the boundary report already flags them as a review item "if upstream ever derives them from
PII." M6-OD-012 (masking format/scope) is OPEN, so the exact scope is an **owner decision**; the pack invents none.
**Fix / decision:** ratify the export masking scope (M6-OD-012) — at minimum bring `messenger_thread_id` to psid
parity. Parallels the M6.2E O-2b messenger_thread_id observation. Interacts with F-SEC-2I-1 (a raw
`messenger_thread_id` can be exported next to a **different** person's raw `comment_id`).

### N-1 — non-finite verified revenue (DQ robustness) *(CODER / DQ; carried from boundary)*

`_verified_revenue` ([funnel.py:148](../impl/M6.2I/app/measurement/funnel/funnel.py)) sums `e.revenue_value` for
`ORDER_VERIFIED` rows with **no `isfinite` / `>= 0` guard**. A `NaN`/`Inf` `revenue_value` on a genuine verified row
poisons the session's `verified_revenue` (propagates to the view / any downstream rollup). Data-quality-integrity
robustness — **not** a PII/secret issue and **not** an in-scope fail gate; the value still only originates from an
`ORDER_VERIFIED` row (RULE-003 holds). **Fix (CODER):** guard the summand (`math.isfinite(v) and v >= 0`), consistent
with the store's set-once revenue discipline.
