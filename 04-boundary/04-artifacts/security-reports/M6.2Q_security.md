## 4. MC-09 (primary) — the decision free-text is exported unmasked

`AdsSpendImportDecision.to_public()` (`models/ads_spend_import.py:68-76`) masks `actor` but exports **`reason`**,
**`audit_ref`**, **`evidence_ref`** **verbatim**:

```
"actor": mask(self.actor),   # masked
"reason": self.reason,       # RAW  ← checker free-text
"audit_ref": self.audit_ref, # RAW
"evidence_ref": self.evidence_ref,
```

`reason`/`audit_ref` are **checker-supplied free-text** typed by a human at approval — the likeliest place (besides a
payload) for accidental PII. A reason like "duyệt cho khách …, SĐT …" would export raw on the durable/export surface.

**Important — the audit trail is already safe.** `import_gate._audit_decision` (`import_gate.py:94-103`) deliberately
does **not** echo `reason`/`audit_ref` into the audit `detail` (only `import_id` + the decision enum; `subject`=actor is
masked by the sink) — the boundary confirmed this (MC10). So the machine audit log is PII-safe; the gap is **only** in
the decision object's `to_public()` export.

*Classification:* same **durable-export masking-scope family** as F-SEC-2K-1 (`status`) / F-SEC-2M-1 (`smoke_id`) —
the code masks the actor id but not a sibling free-text field. *Reachability:* armed-not-fired — no durable-export
surface is wired (the decision lives in the in-memory store; the HTTP bind is the forward M6-OD-011 step), and the
actors are internal ops, not customers. *Fix / route:* **M6-OD-012** decides the durable-export masking scope; the
cheap defense-in-depth is to run `reason`/`audit_ref` through the raw-PII tripwire at import (email-shaped reject is
false-positive-safe) or mask them on export. → CODER + M6-OD-012.

## 5. Access control (doc §22 line 429) — the maker-checker four-eyes (the pack's first real authz control)

Unlike the prior measure-only slices, M6.2Q adds a **genuine authorization control**: the ads-spend import approval is
gated by a **maker-checker (four-eyes) separation of duties** (`import_gate.record_decision`, `import_gate.py:57-92`).
Reviewed on the code:

- **Structurally sound.** An APPROVE is fail-closed refused unless `_canon_actor(decision.actor) !=
  _canon_actor(imp.uploaded_by)` and the checker is non-blank; the distinctness test **canonicalizes** (strip +
  casefold) so a case/whitespace alias of the maker cannot self-approve (a red-team fix over the plan's raw `==`); only
  an APPROVED import materializes; the record store is set-once; a re-decide is refused. `AdsSpendImportDeps` holds no
  network/Marketing-API verb. The API (`POST /api/admin/ads/spend-imports`) requires all of actor/reason/audit_ref/
  evidence_ref (`OWNER_DECISION_INCOMPLETE` otherwise) — the system never synthesizes an approval (RULE-015).
- **The load-bearing caveat — actor identity is UNAUTHENTICATED free-text.** `uploaded_by` and `decision.actor` are
  plain strings from the request body; the gate enforces "two *distinct strings*", not "two *authenticated
  principals*". A single real person can supply `maker="alice"` + `checker="bob"` and satisfy the four-eyes. **The
  control's security value is therefore conditional on the forward M6-OD-011 identity binding** (the HTTP bind + real
  authN/authZ, explicitly out of scope / "separate session"). The boundary's two four-eyes gaps are instances of this,
  armed-not-fired until identity is bound: **MC9** (a Unicode full-width homoglyph of the maker bypasses `casefold` →
  treated as a distinct checker → self-approve) and **N4** (a blank *maker* + any distinct checker → APPROVED — the gate
  refuses a blank checker but not a blank maker).

**Access-control verdict:** the four-eyes control shape is correct and fail-closed for the staged posture, but it is a
**structural** control until M6-OD-011 binds authenticated identity — which is the honest §22 forward condition (per the
P0307 SECURITY_PRIVACY_DESIGN §6: the concrete approver identities are an owner decision). → **owner (M6-OD-011)** for
the identity binding; → **CODER** for two cheap hardenings that make the control robust the moment identity is bound:
**NFKC-normalize before casefold** in `_canon_actor` (closes MC9) and **require a non-blank maker too** (closes N4).

## 6. RULE-003 verified lock — held (the ROAS math is honest)

`SessionRoasReader._verified` (`session_roas.py:101-110`) filters **both** the CPA denominator (verified-order count)
and the ROAS numerator (verified_revenue) on `event_code == ORDER_VERIFIED` — a quote/draft in the window contributes
0 (the M6.2L B4 lock, carried and mirrored). Spend is attributed to a session only when its campaign is **bound** to
the session (`session_for_campaign`) and its `spend_date` is in the derived window; out-of-window / unbound spend →
`daily_total()`, never inflating a session. Divisions are fail-closed (`_safe_div`): spend + zero verified → CPA None,
ROAS 0.0; no bound spend → CPA/ROAS None. This is a security-positive: the revenue side of ROAS cannot count a
non-verified row.

## 7. N1 (F-SEC-2I-1, carried) — the ROAS revenue side is joined by an un-provenanced live_session_id

An asymmetry worth the owner's attention: `session_roas._sessions()` groups **revenue** by each event's own
`live_session_id` (`_session_key`), while `_session_spend` authenticates **spend** via the campaign→session binding. So
a verified-revenue event on a *different* campaign, merely tagged with the bound session's `live_session_id`, is
counted in that session's `verified_revenue` and **inflates its ROAS**. The spend side is authenticated; the revenue
side inherits the standing `live_session_id` provenance gap (**F-SEC-2I-1 / the M6.2I-FUNNEL standing blocker:
single-subject/live_session bind**). *Reachability:* armed-not-fired — the reader is internal (no channel export) and
events come from the trusted measurement store. → **owner** (bind revenue provenance before any real spend/ROAS
surface). Not new to A5, but A5 makes it a money number.

## 8. Value-sanity (N2 / RO10, → CODER) — not PII, but data-integrity + an export-contract break

Neither the spend write nor the revenue write checks finiteness/sign: a **negative** spend/revenue yields a negative
CPA/ROAS, and a **NaN** revenue makes `verified_revenue`/ROAS NaN — and `to_public()` then emits **raw NaN**, breaking
the JSON export contract. Spend is maker-checker-approved (trusted-input) and revenue is Commerce-supplied via a
genuine ORDER_VERIFIED row (no channel writes arbitrary values here), so it is armed-not-fired — but it is the more
reachable twin of a real bug. → CODER: `math.isfinite(v) and v >= 0` on both the spend-import and the verified-revenue
write (RULE-009-adjacent).
