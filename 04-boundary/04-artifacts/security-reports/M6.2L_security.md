## 5. A4 — intake PII-scan scope + unmasked export (F-SEC-2L-1, primary)

A4 adds an **intake path** on the channel-facing `POST /api/ads/events/track` (`app/api/track.py:139-145`) for four
optional M6-owned ad-hierarchy ids (`campaign_id`/`adset_id`/`ad_id`/`live_session_id`), threaded through
`normalize_to_measurement_event()` into Zone A, read back by the resolver.

Two facts, both confirmed on the code:

1. **Intake type-validated, not PII-scanned.** The handler treats the body as untrusted (RULE-H03) — a present-but-non-string/empty
   value is a fail-closed `SCHEMA_INVALID` reject; absent → `None`. But the RULE-014 raw-PII tripwire
   (`_contains_raw_pii`, `track.py:121`) runs **only on the free-text `payload`**, so the four new ids (like the
   pre-existing `page_id`/`session_id`/`guest_id`) bypass it. This is **by design** — the tripwire guards the
   free-text object where user-typed PII lands; structured ids rely on export-time masking.
2. **Export unmasked, psid-only.** Both `AdsAttributionContext.to_public()` (`attribution_context.py:115`) and
   `FunnelTrace.to_public()` (`funnel/models.py:38`) mask **only `psid`** and emit `campaign/adset/ad/live_session_id`
   + `comment_id`/`messenger_thread_id`/`attribution_id` **raw**. This export **predates A4** (M6.2K already emitted
   these; A3 only added `attribution_id`, a non-PII derived ref). A4's genuinely new contribution is that a
   **channel-supplied** value can now populate these fields and feed that pre-existing unmasked export.

**Adjudication (PII classification):**

- `campaign_id` / `adset_id` / `ad_id` → **ad-platform object ids, NOT PII** (they identify advertising objects, not
  people). Masking them would be wrong; and a phone/digit PII-scan would **false-positive legitimate long numeric
  platform ids** — so a blanket digit reject at intake is not safe. No masking action required on these.
- `live_session_id` (+ the siblings `comment_id`, `messenger_thread_id` already exported raw) → live/comment/messenger
  **trace-join ids**. `messenger_thread_id` (a 1:1 DM thread) is the most identifying; this is exactly the **M6-OD-012
  masking-scope** decision and the **same family** as **F-SEC-2I-2** (funnel `messenger_thread_id`), **F-SEC-2J-2**
  (referral `buyer_ref`), **F-SEC-2K-1** (`SmokeResult.status`). The pack consistently masks `psid` and exports the
  join ids raw; the owner (M6-OD-012) decides which join ids are PII-class.

**Reachability:** armed-not-fired — no live export surface (dashboard / funnel / attribution export is unwired; the
track handler's own HTTP routing is the OPEN M6-OD-011 owner integration step). A channel-supplied value cannot leave
Module 6 today.

**Fix / route:** M6-OD-012 (masking scope) decides masking for `live_session_id`/`comment_id`/`messenger_thread_id`.
For defense-in-depth at intake I **concur with the coder's proposal**: add an **email-only** reject on the ad-hierarchy
ids — it is false-positive-safe (no legitimate campaign/adset/ad/live_session id is email-shaped), catching the one PII
shape that can never be a valid platform id, at zero cost to the numeric ids. A phone/digit reject is **not** safe here.
