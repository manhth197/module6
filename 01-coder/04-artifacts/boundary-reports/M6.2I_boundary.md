## 3. Verdict on the in-scope fail gates

### M6-FAIL-001 — Revenue misuse (verified-only revenue, RULE-003) — **NOT TRIPPED**

The funnel's `_verified_revenue` is a **self-enforcing choke** — it sums `revenue_value` **only** from rows whose
`event_code == 'ORDER_VERIFIED'` AND that carry a revenue value. Executed:

- A `QUOTE_SENT` / `ORDER_CREATED` / the full taxonomy (quote/cart/draft/payment-waiting/cod-waiting) count in their
  funnel **stages** but contribute **0** revenue (A1–A3, SMK-004).
- **A quote row force-carrying a `revenue_value`** (via the store's `materialize(verified=True)` misuse, or a
  mismatched event↔conversion pairing) **still contributes 0** — the funnel ANDs the event code with revenue
  presence (A4). This directly closes the **M6.2F F-DASH-1** gap (the M6.2F mart trusted `revenue_value` alone; the
  funnel re-checks the row's own event code). `PAYMENT_COMPLETED` force-carrying revenue → 0 (A5).
- A genuine `ORDER_VERIFIED` row **is** counted (A6, discriminating); the funnel and the M6.2F dashboard agree 0
  revenue / no ROAS for a quote-only store (A7).

The only way to make a non-verified row read as revenue is the type-confusion **F-FUNNEL-1** (§4) — which needs
in-process code execution twice over and is not channel-reachable.

### M6-FAIL-010 — Phase jump (RULE-016; Phase-2 must measure only) — **NOT TRIPPED**

- **The funnel is measure-only.** `GoldenHourFunnel` / `RetargetingMeasurement` expose **no**
  start/close/open/emit/transition/operate/send/dispatch/scale/publish/order-state verb (B1); the `golden_hour`
  module has **no** session controller — `observe_state` only labels a consumed signal, fail-closed to UNKNOWN, and
  never assumes PRE/LIVE (B2/B5); `assemble()`/`view_for()` mutate nothing (B3).
- **No later-phase reach.** The funnel package imports no scale/learning/outbox/dispatcher/transport module (B4), and
  the **transitive** import graph (which pulls the dashboard package via `kpi_metrics._safe_div`) contains **zero**
  Phase-3 modules — phase order is not crossed at import time either (W4). A token sweep finds 0 session/send/scale/
  publish/order-state action defs (E1).
- **Ledger:** the first Phase-2 slice entered only after the full Phase-1 chain SIGNED (§1) — no phase jump.

## 4. The primary residual — F-FUNNEL-1 (armed-not-fired; the sharpest finding)

**What:** the revenue choke `getattr(e, 'event_code', None) == REVENUE_VALID_EVENT` is a Python `==`, which
dispatches to the left operand's `__eq__`. A **`str` subclass** whose `__eq__` returns True (and `__hash__` hashes
as `'ORDER_VERIFIED'`), used as a `QUOTE_SENT`-content row's `event_code`, plus an `object.__setattr__` to stamp a
`revenue_value` past the store's insert guard, makes the funnel count **9,000,000** as verified revenue from a
quote-content row (W1). It also flips that row's Verified-Rate numerator and `ORDER_TO_VERIFIED` stage.

**Why it is NOT a live FAIL-001 breach (reachability):** it requires **arbitrary in-process code execution twice
over** — (1) a `str` subclass as `event_code`, which **ingest never produces** (channel input is plain JSON strings,
Core-registry-validated, RULE-001), and (2) an `object.__setattr__` to bypass the store guard that rejects a
revenue-bearing insert. No channel (comment / Messenger / ad copy / form / API / CRM payload / webhook) can produce
either. At that level of compromise every in-memory invariant is moot (the attacker could fabricate a genuine
ORDER_VERIFIED row directly). So it is armed-not-fired.

**Why it still matters:** it is a genuine **defense-in-depth inconsistency**. The consent-scope path was
*deliberately hardened* against exactly this `str`/subclass type-confusion class (the M6.2B/Round-4 MAJOR-7 "F2"
fix — coerce-or-deny, materialize a real `frozenset`), but the **same discipline was never applied to the revenue
event-code equality**. **Fix (CODER):** compare via `type(e.event_code) is str and e.event_code == REVENUE_VALID_EVENT`
(or canonicalize the code), mirroring the scope-path hardening; the same applies to `stage_for`/`_count_code`.

## 6. Residuals & notes (none trips an in-scope gate; all armed-not-fired)

**F-FUNNEL-1** *(CODER, primary — W1).* Revenue-choke type-confusion; not channel-reachable; a defense-in-depth
inconsistency vs the hardened consent-scope path. Fix: `type(e.event_code) is str and e.event_code == 'ORDER_VERIFIED'`
(and the same on `stage_for`/`_count_code`). See §4.

**F-FUNNEL-2** *(CODER — W2).* The funnel `dict()`-copies its two consumed maps (golden-hour, capture) at
construction but reads each event's `attribution_context` **live**, so a hostile `Mapping.get` executes attacker
code inside `assemble()` (here it drove a `store.materialize` Zone-B write). In-process only (the injector already
has store capability; the store's set-once / forbidden-op guards remain the backstop), but a real inconsistency.
**Fix:** snapshot `ctx = dict(ctx)` (or the three trace keys) before reading — which also closes F-FUNNEL-3.

**F-FUNNEL-3** *(CODER — W3).* The same un-snapshotted `attribution_context` makes the projection non-deterministic:
a plain mutable ctx mutated between `assemble()` calls changes the session grouping/trace (measurement drift /
non-repeatable evidence). Revenue/capture are unaffected (they key off the row's own fields). **Fix:** same
`dict(ctx)` snapshot.

**F-FUNNEL-4** *(CODER + M6-P1806 — W5).* `_trace` folds `comment_id` / `messenger_thread_id` / `psid` with a
per-field `x = x or ctx.get(x)` across **all** events sharing a `live_session_id`, with no subject/consent binding —
so two people whose events share one session key are stitched into one trace (personA's comment next to personB's
thread + masked psid). Even with psid masked, the export **asserts a false association** between two identifiable
people (attribution-integrity + PII). **Fix:** bind the trace to a single subject (the conversion's
`customer_or_guest_key`), or record per-subject traces.

**Notes:**
- **N-1** NaN/Inf revenue on a genuine verified row poisons `verified_revenue` (no `isfinite`/`>=0` guard in the
  store or the funnel sum) (A8 / RI-004) → DQ robustness, M6-P1806. **N-2** frozen-view `object.__setattr__` (W6)
  and the str-subclass (W1) both need arbitrary in-process code execution — process-integrity notes, not
  channel-reachable. PII belt: `live_session_id` / `comment_id` / `messenger_thread_id` are exported raw as trace
  ids (assumed non-PII identity-boundary fields) — a M6-P1806 review item if upstream ever derives them from PII.
