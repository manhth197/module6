## 4. Open findings (executed; armed-not-fired — none trips M6-FAIL-002)

### F-A — [MINOR] the dispatchers **raise** on a hostile consent adapter (`permits_send` / `current_state` / duck-attr unwrapped in `_policy_block`)
**File**: `measurement_dispatcher.py:76-87`, `audience_dispatcher.py:67-77`, `enqueue.py:124-128` — the consent
`reader.get(...)` is wrapped in `try/except`, but the subsequent `permits_send(...)` (dispatchers) and
`consent_gate.evaluate(...)` (audience enqueue) are **not**; `permits_send` (`gate.py:88-97`) calls
`consent_reader.current_state(subject_ref)` and `evaluate` reads `snapshot.consent_state` — neither is guarded.
**Rule/contract**: the "forgiving worker" expectation (the M6.2A/B F1 class) · **Direction: crash + lost audit +
drain-batch DoS** (never a send, never a consent grant).

Executed (`F1-*`, `W-R5`):

- `F1-get-raises` — a consent reader whose `get` raises is **handled** (wrapped → `snap=None` → consent deny →
  DEAD_LETTER). ✅
- `F1-currentstate-raises` — a reader whose **`current_state`** raises → `RuntimeError` **escapes `run_once`**.
- `F1-duck-attr-raises` — a reader that returns a duck lacking `consent_state` → `AttributeError` in `evaluate`
  **escapes `run_once`**.
- `W-R5-enqueue-duck` — the same gap at the **audience enqueue**: `enqueue_audience_sync` wraps `consent_reader.get`
  but not `consent_gate.evaluate`, so a duck snapshot raises `AttributeError` mid-loop → a partial, unaudited enqueue.

**Why MINOR, not a gate trip.** The exception fires **inside** the policy check, **before** `attempt_delivery`, so
**no send happens** — it is fail-closed in the send direction, and M6-FAIL-002 is not tripped. The damage is (1) a
lost audit line for that item and (2) — because `run_once` iterates `due_items` and one un-caught `_process` abort
ends the whole loop — the remaining due items in that batch are **not processed** (a hostile consent adapter can
stall the drain). It needs a **hostile / faulty consent adapter** (the wired `InMemoryConsentReader` is honest), so
it is not reachable from channel input today, but it becomes live the moment a real DB-backed consent adapter can
error at `current_state`.
**Fix (coder)**: wrap `permits_send` / `evaluate` (and the `dq_status` hook) the same way `reader.get` is wrapped
→ on any exception, fail-closed to a `POLICY_BLOCK:CONSENT_CHECK_FAILED` terminal (audited), so one bad item cannot
abort the batch; equivalently, harden `permits_send`/`evaluate` to treat an unusable snapshot as deny.

### F-B — [MINOR] a lying `set`-subclass `consent_scope` defeats the F2 guard (consent fail-OPEN residual)
**File**: `gate.py:56-68`. **Rule/gate**: RULE-002 / M6-FAIL-002 · **Direction: fails OPEN** (grants a scope never
held) · **armed, not fired**.

The F2 guard validates the container **type** (`set`/`frozenset`) and its **elements**, but the grant decision
`scope not in snapshot.consent_scope` (`gate.py:68`) dispatches to the container's `__contains__`. A `set` subclass
with an overridden `__contains__` that returns `True` — and an **empty backing** so the element-type
`all(isinstance(s, ConsentScope) …)` is **vacuously** True — passes F2 and reads as granting a scope it never held.
Executed (`W-MDC01-lyingset`): a `ConsentSnapshot` subclass carrying such a lying set → measurement dispatch →
`permits_send` returns True → `attempt_delivery` → **SENT** (with the injected succeeding transport).
**Ceiling.** Armed-not-fired: the **staged** transport blocks the real send, and it needs a **compromised consent
adapter** returning a booby-trapped subclass — a real `ConsentSnapshot` coerces its scope to a plain `frozenset` in
`__post_init__` (honest `__contains__`), so it cannot carry a lying set. It becomes live only at M6.2D **and** only
against a hostile consent system-of-record.
**Fix (coder)**: materialise the scope before the membership test — `scope in frozenset(snapshot.consent_scope)`
iterates the actual elements and bypasses a lying `__contains__` (this is the gate-level completion of F2).

### F-C — [MINOR] the audience path never binds `member_key` to the consent snapshot's subject (borrowed consent)
**File**: `enqueue.py:122-129` (+ `audience_dispatcher.py:75`). **Rule/gate**: RULE-002 / M6-FAIL-002 ·
**Direction: fails OPEN** (an un-consented member synced on someone else's consent) · **armed, not fired**.

`enqueue_audience_sync` fetches the snapshot by `member.consent_snapshot_id` and evaluates it, but **never asserts**
the snapshot's `subject_ref` corresponds to `member.member_key`; the dispatcher's `permits_send` likewise checks
`current_state(snap.subject_ref)` — the **snapshot's** subject, not the member. So a segment-membership row that
(mis)points a member at **another** subject's VALID consent → that member is **ADD**ed on **borrowed consent**.
Executed (`W-AUD02-borrowed`): `mem_victim` whose consent ref resolves to `guest_mapped_ok`'s VALID consent →
operation **ADD**.
**Ceiling.** Armed-not-fired: the staged transport blocks; and it needs a **mispointed CRM membership**
(`customer_segment_members` is CONSUMED, RULE-018 — M6 reads it). The **measurement** path DOES bind consent to the
event's subject (the M6.2A ingest MAJOR-2 fix); that subject-binding was **never applied to the audience path**.
**Fix (coder)**: before treating a member as ADD-eligible, bind `member.member_key` to `snap.subject_ref` (or a
trusted mapping), mirroring the ingest seam's `_subject_bound`.
