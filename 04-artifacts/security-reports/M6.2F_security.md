## 7. Findings (detailed)

### F-VIEW-1 — the 0008 dashboard support view exposes the raw `attribution_context` (incl. raw `psid`) (MEDIUM, latent) — my finding → CODER + M6-OD-012
**File**: `migrations/0008_create_ads_dashboard_support_view.sql` (the `CREATE VIEW ads_dashboard_kpi_source` SELECT
list includes `attribution_context`, `page_id`, `live_session_id`). **Rule/gate**: RULE-014 (no raw PII to a
consumer); relates to FAIL-008 (not in this prompt's in-scope gate set), **not tripped** (no live exposure).
The view is the future DB-backed dashboard read path (granted `SELECT` to `ads_dashboard_reader` at M6-OD-011). Its
`attribution_context` column carries the raw `psid` (M6.2E `as_stored()` keeps psid raw for trace joins), so a reader
of the view would see raw psid — a **broader** exposure than the app, which computes aggregates and never reads psid.
**Why latent:** the view is STAGED (`live_migrations=false`, never applied) and the running app does not use it, so
there is **no leak today**. It becomes a real PII exposure at the M6-OD-011 binding.
**Fix (CODER, before the binding):** drop `attribution_context` from the view (the aggregates don't need the raw
blob), or replace it with a projection of only the non-PII attribution fields (campaign/adset/ad/entry_channel/
confidence/conflict), or mask `psid` in the view — aligning the view with the app's PII-safe posture and M6-OD-012.

### F-DASH-2 — `attribution_context` is a mutable dict inside a frozen row (MINOR, armed-not-fired) — routed → CODER (concur)
An in-place edit of the stored `attribution_context` dict defeats the "set-once immutable snapshot" claim (can flip a
DQ Attribution HOLD→PASS or re-route the CRM/Diamond revenue breakdown); **total revenue is unchanged** → not FAIL-001.
**Fix (CODER):** store `attribution_context` as `MappingProxyType`/copy-on-read.

### N-4 — `mask()` reveals 5/6 of a 6-char id (Observation → M6-OD-012)
`mask('OD1234')='OD1***34'` reveals first-3 + last-2 (5 of 6 chars). This is the parameterized M6-OD-012 default; for
short ids the reveal threshold could be tightened (e.g. reveal at most ⌊len/3⌋). An owner/privacy-legal call.

### N-1 / N-2 — non-finite / negative revenue (Observations → DQ / CODER)
N-1: a NaN/Inf `revenue_value` poisons the total and breaks the set-once idempotent replay (carried M6.2E O-5). N-2:
a negative `revenue_value` is accepted (understates — never inflates — so not FAIL-001); no `≥0` check.
**Fix (CODER):** reject non-finite (`math.isfinite`) and negative revenue at the conversions endpoint / DQ gate.

### Revenue / data-mart-trigger — corroboration (the in-scope pillars)
FAIL-001 and FAIL-005 are held (executed by M6-P1505, concurred from code): verified-only revenue by construction;
`DataMart` read/aggregate-only (no trigger/write/send); endpoint no side effect; DQ worker writes only the audited
Zone-C status. The revenue contract-hardening residuals **F-DASH-1** (materializer/store don't assert the row's own
`event_code==ORDER_VERIFIED`) and **F-DASH-3** (two verified rows sharing `order_code` double-count) are
**armed-not-fired** — the materializer is wired only in tests, so no channel path books mispaired/duplicate revenue in
the staged app — and are routed to CODER; **F-DASH-4** (scale-eligibility ignores the DQ overall) is AND-gated by
`SCALE_MODEL_RATIFIED=False` with no in-slice consumer and is routed to the **mandatory M6.2G scale re-gate**.

### Untrusted-input handling
`GET /api/admin/ads/dashboard`'s `query` is untrusted admin DATA — read-only, unknown keys ignored, never executed
(RULE-H03; boundary B4: a malicious dict with a `trigger`/`scale` callable / SQL string is ignored). No untrusted
value reaches a sink or the response unmasked.
