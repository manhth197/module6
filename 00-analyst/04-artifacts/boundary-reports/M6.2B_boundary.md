## 4. Open findings (all executed; all armed-not-fired — none trips M6-FAIL-003)

### F-A — [MINOR] the endpoint's `handle_track_request` **raises** on a hostile body (its pre-seam PII scan + hash are unwrapped)
**File**: `track.py:121` (`_contains_raw_pii(payload)`, unwrapped) → `track.py:225-241` (`_iter_strings`, unbounded
recursion); `track.py:127` (`raw_event_hash = _raw_event_hash(body)`, unwrapped) → `track.py:244-253`
(`sorted(body.keys())` + `json.dumps(..., default=str)`).
**Rule/contract**: RULE-H03 "the handler is a pure function over an UNTRUSTED body"; the F1 "never raises" contract
· **Direction: availability + lost audit** (never a grant, never a drift).

The two untrusted-body walks at the head of the handler run **before** the hardened seam (which F1 made
never-raise) and are **not** wrapped. Executed (`RB-*` / `W-*`):

- **`RB-deepnest` — REACHABLE from a real JSON body.** A ~4,000-deep nested `payload` (valid JSON) → `RecursionError`
  escapes the handler (unaudited 500). A malicious client can crash the endpoint with a well-formed nested body.
- Non-JSON-only variants (need a direct in-process caller, not a JSON body): `W-mixedkeys` (mixed str/int body keys
  → `sorted()`/`json.dumps(sort_keys=True)` `TypeError`), `W-hostiletz-ep` (`event_ts` as a `datetime` carrying a
  `tzinfo` whose `utcoffset()` raises → `str()` in `_raw_event_hash` raises **before** the seam's F1 guard runs),
  `W-circular` (a circular `payload` → `RecursionError` in `_contains_raw_pii`).

**Why MINOR, not a gate trip.** A raised handler logs **nothing** (the crash is before any store write), so no
unregistered event drifts into `web_event_logs` or `ads_measurement_events` — M6-FAIL-003 is not tripped. The damage
is a 500 + a lost audit line for that request — exactly the data-loss shape F1 closed at the seam, re-surfacing at
the endpoint's own pre-seam code. It becomes live the moment M6.2B is wired to the real HTTP framework (a deeply
nested JSON body is trivially sendable).
**Fix (coder)**: wrap `_contains_raw_pii` and `_raw_event_hash` (steps 6–7) in the same audited-deny pattern the
seam uses (→ `REJECTED` + audited `SCHEMA_INVALID`/`PAYLOAD_UNPROCESSABLE`), and bound payload nesting depth /
iterate instead of recursing.

### F-B — [MINOR] the server-side `raw_event_hash` is over-broad, so cosmetically-different copies of one event **over-count**
**File**: `track.py:244-253` (`_raw_event_hash` canonicalizes the **raw** `event_ts` string and **every**
non-volatile body key) vs `idempotency.py:23-39` (`normalize_ts` collapses tz notations and drops microseconds in
the `normalized_ts` component).
**Rule/gate**: RULE-005 / SMK-003 dedup intent · **Direction: over-count** (never event drift, never a grant).

The RULE-005 key = `event_code|page_id|session_id|raw_event_hash|normalized_ts`. `normalize_ts` canonicalizes the
`normalized_ts` component (the MAJOR-4 fix), but the new `raw_event_hash` re-introduces the raw `event_ts` string
(and every extra body field) into the key, so two **cosmetically different** encodings of the **same logical event**
fork the key → a 2nd row in **both** stores. Executed:

```
DEDUP-tznotation : same instant  '…T12:00:00+07:00'  vs  '…T05:00:00+00:00'   -> web=2  meas=2
W-subsecond      : same second   '…T12:00:00+00:00'  vs  '…T12:00:00.500000+00:00' -> web=2  meas=2
W-junkkey        : identical body + one extra ignored key {"_nonce":"1"}     -> web=2  meas=2
```

**Honest ceiling.** This is **not** a SMK-003 violation: a byte-identical replay (the "Duplicate Pixel/CAPI/Offline"
scenario) **does** dedup — proven by `DEDUP-replay` (1 row each). And it is **not** event drift (M6-FAIL-003): the
extra rows are the same *registered* event. It is an over-count on a **non-exact-replay** — a client that retries
with a re-serialized timezone, sub-second precision, or an appended nonce double-logs. Severity MINOR (dedup quality
/ DQ), owner-visible.
**Fix (coder)**: hash a **canonical** projection — use `normalize_ts(event_ts)` (not the raw string) and restrict the
canon to the known CTR-016 contract fields — so the hash matches the key's own canonicalization.
