### 3.1 M6-FAIL-001 (revenue / scale evidence) — NOT tripped

- **LOW/HOLD/conflict is never scale evidence, doubly fail-closed** (RULE-009). `SE-eligible-matrix`:
  `is_scale_evidence_eligible` is True for **exactly one** of the 12 confidence×conflict combos — `(HIGH, NONE)`;
  every LOW/MEDIUM and every conflict (`MULTI_TOUCH` / `MISSING_SOURCE` / `DUPLICATE_RISK`) → False.
  `SE-unratified-highnone`: even a `HIGH+NONE` snapshot has `scale_evidence=False` while `SCALE_MODEL_RATIFIED=False`.

  eligibility gate holds). `SE-materialize-low`: a missing-source verified order → LOW / `MISSING_SOURCE`, revenue

- **Grading is fail-closed** (`SE-grading`, 10 source shapes, 0 mismatches): missing → LOW; duplicate-risk → LOW;

  spurious `crm` signal onto a complete-ad source **degrades** it to `MULTI_TOUCH/LOW` — a caller signal cannot
  *inflate* confidence.
- **Revenue only from ORDER_VERIFIED, set-once** (RULE-003 / RULE-008). `REV-nonverified-*`: a `VIEW_LANDING` /
  `PAYMENT_COMPLETED` conversion (even carrying a `revenue_value`) materializes with revenue **None**. `REV-setonce`:
  a verified revenue is immutable — an identical re-materialize is a no-op, a **different** value raises
  `MeasurementStoreViolation`, the row stays `100000.0`. `REV-requires-order`: revenue without an `order_code` →
  violation. `REV-store-guards`: a revenue-bearing Zone-A insert + `update`/`delete` all raise.

## 4. Open finding (executed; armed-not-fired — does not trip an in-scope fail gate)

### F-G — [MINOR] the adjustment path is under-validated (accountability / immutability-completeness gap)
**File**: `materializer.py:103-134` + `adjustment.py:18-30,46-55`. **Rule**: RULE-008 (a correction "requires an
adjustment record with actor, reason, audit and evidence") · **Direction: weak accountability record** — but
**never a row mutation**, so M6-FAIL-004 is not tripped. Three executed sub-gaps of the same class:

- **`ADJ-empty-fields`** — `request_adjustment(actor="", reason="", audit_ref="", evidence_ref="", …)` is
  **accepted**; the required fields exist but are empty, so the record satisfies RULE-008 only nominally (no real
  WHO/WHY/AUDIT/EVIDENCE).
- **`W-ADJ2-noexist`** — `request_adjustment` **never checks that the target row exists or is verified**; an
  adjustment can be recorded against `"no_such_event"`.
- **`W-ADJ6-mutable`** — `AdjustmentRecord` is frozen but its `proposed` is a plain `dict`, so a caller holding a
  reference can **mutate `records[0].proposed` in place after append** — the append-only *log* is immutable but a
  record's `proposed` contents are not.

**Why none is a gate trip:** in every case the verified row's revenue/attribution is **unchanged** (the adjustment
is an overlay that is never applied to the row), so it cannot override Core or inflate revenue. These are
data-quality / accountability / immutability-completeness gaps.
**Fix (coder)**: reject an adjustment whose `actor`/`reason`/`audit_ref`/`evidence_ref` is empty/whitespace; assert
the target row **exists and is verified** before recording; and store `proposed` as an immutable mapping
(`MappingProxyType` / copy-on-read). Optionally constrain `proposed` to an attribution/revenue field allow-list (O-1).

### 4.2 Observations (not defects — recorded so the owner decides knowingly)

- **O-1 — `AdjustmentRecord.proposed` has no field allow-list** (`COMM-proposed-echo`). A caller can place an
  arbitrary key (e.g. a `commission_value`) in `proposed`; it is **stored in the record but never computed or
  applied** to any row, so RULE-019 (no commission *math*) holds — the module records a caller *assertion*, it does
  not compute commission. Constraining `proposed` to the attribution/revenue fields is an M6-P1406 hardening note.
- **O-2 — the durable Zone-B `attribution_context` keeps the raw `psid`** (`OVR-psid`, attribution_context.py:121-127).
  `to_public` masks `psid` on every export; `as_stored` keeps the raw value for durable trace joins. PII-in-the-durable-
  store (the O1/O2 pattern from earlier slices) is **M6-P1406 / M6-OD-012** scope, not FAIL-001/004.
- **O-3 — a carried M6.2A ingest raw-subject comparison remains flagged** (coder's IMPLEMENTATION_NOTES §Round 2).
  `ingest.py`/`identity/resolver.py` compare `snapshot.subject_ref == guest_id` on the **raw** value; a hostile
  `ConsentSnapshot` subclass with a raising `subject_ref` property could raise there (not routed through
  `safe_subject_ref`). It is FAIL-002-adjacent (out of this prompt's FAIL-001/004 scope), armed-not-fired
  (external_send=OFF), and the coder flagged it for a later hardening — recorded here so it is not lost.
- **O-4 — the materializer's `verified_event_codes` is a constructor arg, not channel input** (`W-REV7-miswire`,
  materializer.py:47). The default is `("ORDER_VERIFIED",)` (correct); a **mis-wired** assembler passing
  `("VIEW_LANDING",)` would book revenue for a non-verified event. Not channel-reachable (an assembly discipline
  concern), so not a live FAIL-001 — a wiring note for the CODER / integration step.
- **O-5 — a NaN/Inf `revenue_value` breaks the set-once idempotent replay** (`W-REV8-nan`). Because `NaN != NaN`,
  the store's "same value?" check (measurement_event_store.py:90-96) treats an honest replay of a NaN-revenue
  verified row as a *different* value and raises. The root cause is non-finite revenue itself (the M6.2D O-4 DQ
  gap); the M6.2F DQ checker / M6-P1406 should reject a non-finite `revenue_value`. Not a FAIL-001 over-count.
