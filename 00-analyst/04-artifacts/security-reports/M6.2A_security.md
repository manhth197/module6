## 3. Pillar 1 — Raw PII scan (RULE-014 / H02) — **CLEAN (residual latent)**

**Masking is centralized and correct.** `app/measurement/masking.py::mask()` strips control / non-printable chars
**first** (so a masked value can never carry a raw control char, and a short id can't be padded past the reveal
threshold), then reveals at most 3 leading + 2 trailing chars only when ≥1 char stays hidden; a value ≤5 chars is
**fully** masked (`MASK_SHORT`). Format is the M6-OD-012 pack default `abc***xy`, parameterized from `app/config.py`.

**Every identity value is masked before it can reach the audit trail:**

- `audit.py::AuditLog.record()` masks `subject` at the boundary (`subject_masked=mask(subject)`) — a caller cannot leak
  a raw identity by accident, even when it passes a raw `guest_id` (e.g. `resolver.py`, `ingest.py` subject-mismatch).
- `consent/gate.py` passes `subject=snapshot.subject_ref` into `record()` on every deny branch → masked there.
- `identity/resolver.py` masks **all** identity values it emits — `mask(guest_id)`, `mask(gc.mapped_customer_id)`, and
  even the audit ref (`detail=f"audit_ref={mask(gc.mapping_audit_ref)}"`). `subject_matches()` compares raw ids **in
  memory only** and returns a bool — raw ids never leave the method.
- `models/consumed.py::PII_FIELDS` labels the PII-class fields (`guest_id`, `contact_fingerprint`,
  `mapped_customer_id`, `subject_ref`) so masking/audit know what to protect; `contact_fingerprint` is treated as
  PII-class **even though it arrives already hashed** from Customer-identity (M6 only reads it).

**The append-only measurement table legitimately holds pseudonymous ids — not a masking violation.**
`web_event_logs` (`models/web_event_log.py`, DDL `migrations/0001`) stores `page_id`, `session_id` (labeled
PII-pseudonymous), `source`, `correlation_id` as raw `TEXT`. This is the **operational measurement record**, not "a log
or evidence" in the RULE-014 sense; **none** of these fields is copied into an `AuditRecord` or into evidence by this
slice, the store is **in-memory** (staged; `live_migrations=false`), and nothing serializes it (§2 sink sweep). The DDL
comment directs masking of `session_id` when it reaches logs/evidence (**M6-OD-012**). Recorded as **O1** (§7).

**Untrusted-type handling at the seam is strong and PII-safe.** `ingest.py` opens with a **type boundary** that
type-checks every channel-origin scalar; a wrong-typed field is audited **by field NAME only** (`detail=f"field={name}"`)
— the offending, possibly attacker-shaped value is **never** handed to the audit sink (`_require_str`,
`_field_type_reject`). A bad `event_code` never even reaches the typed result fields.

**One raw-PII hygiene gap remains — `SEC-PII-01` residual (§7).** The single place a channel-controlled value can enter
an audit record verbatim. In the staged slice it produced **no** actual leak (§2 clean; no durable/exported sink), which
is why it is latent, not a tripped gate.

### SEC-PII-01 — identifier-shaped `event_code` still persisted verbatim into the audit trail (MEDIUM, **PARTIAL fix**, latent) — = boundary MINOR-9
**Files**: `app/measurement/audit.py` (`_EVENT_CODE_SHAPE`, `_safe_event_code`, `AuditRecord.event_code`) ·
`app/measurement/registry/validator.py` (REJECT/HOLD branches pass the caller's `event_code` into `audit.record(...)`)
**Rule/gate**: RULE-014 / H02 (PII masking); relates to FAIL-008 ("PII in a **log**") — **not** in this prompt's in-scope
gate set, and **not tripped** (no PII reached any sink; §2 clean).

**Coder fix present and verified.** `_safe_event_code` keeps a code **verbatim only** when it matches
`\A[A-Za-z0-9_.:\-]{1,64}\Z`; anything else (email `@`, whitespace, control chars, >64 chars, embedded newline — the
`\A..\Z` anchors reject a trailing-newline bypass) is wrapped `INVALID_EVENT_CODE[{mask(printable)}#{sha256[:8]}]`. This
**closes** the Round-1 blob/email/control-char/oversize class — the most dangerous shapes are now masked + hashed while
the reject **reason** (a separate field) preserves SMK-001 "audit rõ".

**Residual (narrowed, = boundary MINOR-9).** The allowlist admits `0-9`, so an **identifier-shaped** `event_code` — a
bare digit-run of VN-mobile shape, or an underscore/colon-joined numeric id, ≤64 chars — **matches** and is stored
**verbatim** in `AuditRecord.event_code`. The REJECT branch (`UNKNOWN_EVENT_NOT_IN_REGISTRY`) is *by definition* where
`event_code` is channel-controlled untrusted DATA, and the documented next caller is **M6.2B**'s untrusted HTTP body.

**Why still latent, not a tripped gate.** The audit sink is an in-memory list (`audit.py::AuditLog._records`),
**non-durable** (`M6-OD-011=STAGED_ONLY`, `live_migrations=false`) and **never serialized/logged/exported** (§2 sink
sweep = clean). So there is **no actual leak now**. It escalates the moment any of: (a) the audit sink is bound durable
at the M6-OD-011 integration step; (b) a serializer/evidence dump renders audit records; (c) M6.2B wires the untrusted
HTTP body to this seam.
**Fix (CODER, before any of those bindings):** tighten the "keep verbatim" shape to the real registry-code grammar so a
pure digit-run / identifier-shaped token does **not** pass (a legitimate near-miss registry code still reads clearly;
a bare numeric id gets the masked+hashed wrapper). Complete this before M6.2B.
