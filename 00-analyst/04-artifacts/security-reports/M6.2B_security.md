## 7. Findings (detailed)

### MINOR-9-res — identifier-shaped `event_code` still stored verbatim (LOW–MEDIUM, latent) — routed to M6-P1106 (me)
**File**: `app/measurement/audit.py` (`_IDENTIFIER_DIGIT_RUN = \d{6,}`, `_IDENTIFIER_PREFIX` finite list,
`_looks_like_identifier`, `_safe_event_code`).
**Rule/gate**: RULE-014 / H02; relates to FAIL-008 ("PII in a log") — **not** in this slice's in-scope gate set and
**not tripped**.

The M6.2B coder extended the M6.2A SEC-PII-01 fix with `_looks_like_identifier`, which wraps a token that has a digit
run ≥6 (so **VN phones, 10–11 digits, are caught**) or starts with a listed id prefix (`cust|guest|psid|ord|order|
user|uid|fbid|ig|acct`). This is a **denylist**, so it is inherently incomplete: a token that matches the code shape
`[A-Za-z0-9_.:\-]{1,64}` but has a **<6-digit run** or an **unlisted prefix** (e.g. `sess_…`, `token.…`, a hex handle
with no 6-run) still passes `_safe_event_code` and is stored **verbatim** in the in-memory audit sink (via the
`UNKNOWN_EVENT`/`TRACK_REJECTED` branches where `event_code` is channel-controlled).
**Why latent:** the audit sink is in-memory, non-durable (`M6-OD-011=STAGED_ONLY`), and never serialized/exported
(§2 sink sweep clean) — no actual leak now. It escalates when the sink is bound durable / serialized / fed hostile
bodies at the M6-OD-011 HTTP binding.
**Fix (CODER):** replace the denylist with an **allowlist** — keep an `event_code` verbatim only when it matches the
real registry base-event grammar (the locked codes are UPPER_SNAKE, `VIEW_LANDING..ORDER_VERIFIED`); wrap everything
else. This closes the whole identifier-shaped class in one rule instead of chasing prefixes, and still preserves
SMK-001 "audit rõ" via the separate, untouched reason field.

### O-1 — the endpoint PII tripwire scans `payload` only (MEDIUM, latent) — routed to M6-P1106 (me)
**Files**: `app/api/track.py:121` (`_contains_raw_pii(payload)`), `:236-241` (`_iter_strings`/`_contains_raw_pii`),
`:129-132` (top-level `page_id`/`session_id`/`source`/`guest_id` taken as-is) → `ingest.py`/`normalize.py` store them
raw in `web_event_logs` / `ads_measurement_events`.
**Rule/gate**: RULE-014 / FAIL-008 — **not** in this slice's in-scope gate set and **not tripped**.

The tripwire refuses raw PII in the optional `payload` object, but the top-level identifier scalars are **not** scanned
and **not** charset-constrained. `source` is explicitly "channel-origin = untrusted DATA", and `guest_id` is PII-class.
A raw email/VN-phone placed in `source`/`session_id`/`page_id`/`guest_id` therefore bypasses the tripwire and lands
**raw** in the durable rows. The tripwire's partial coverage also gives a **false sense of completeness**.
**Why latent:** the stores are in-memory (staged), the values are masked on every export/audit surface (O1), and no
sink serializes them (§2) — no actual leak now. It becomes a FAIL-008-class issue when `web_event_logs` /
`ads_measurement_events` are bound durable at M6-OD-011.
**Fix (CODER):** extend `_contains_raw_pii` (or, better, a positive pseudonymous-id charset/length validation) to the
top-level `session_id`/`page_id`/`source`/`guest_id` **before** they reach the durable rows; keep the
store-raw / mask-on-export design (M6-OD-012) for the fields that are legitimately pseudonymous.
